# Phishing Email Investigation — Domain Impersonation / Transfer-Fraud Lure

**Type:** Independent security investigation (portfolio / lab practice)
**Date:** 28 July 2026
**Classification:** Phishing — Domain Impersonation / Transfer-Fraud Pretext
**Severity:** Medium — spoofing succeeded due to unenforced DMARC; no evidence of compromise, credential loss, or financial impact at time of analysis
**Tools used:** Gmail header export, DMARC/SPF/DKIM checker, ARIN RDAP/WHOIS, domain WHOIS

---

## 1. Executive Summary

A phishing email with the subject *"Update Regarding Your Transfer Request"* was received, purporting to originate from `imperialtrustgroup.com`. Header analysis, DNS authentication review, and WHOIS/RDAP research confirmed the message is a spoofed impersonation attempt sent through shared Hostinger hosting infrastructure.

The impersonated domain, `imperialtrustgroup.com`, was registered only **44 days** before the email was sent, uses DNS-parking nameservers, and hosts no live website — strong indicators of purpose-built phishing infrastructure rather than a legitimate business. The email reached the inbox only because the impersonated domain's DMARC policy is not enforced (`p=NONE`), allowing an unauthenticated message through despite failing DMARC alignment.

## 2. Source Material

- Full email headers (Gmail "Show original" export)
- DMARC / SPF / DKIM authentication test results (third-party DMARC checker)
- IP WHOIS / RDAP record for `23.83.213.23` (ARIN)
- Domain WHOIS records for `main-hosting.eu` and `imperialtrustgroup.com`

## 3. Header Analysis

| Field | Value |
|---|---|
| From (displayed) | `imperialtrustgroup <wordpress@imperialtrustgroup.com>` |
| Return-Path (actual) | `<noreply@srv2026.main-hosting.eu>` |
| Received-SPF | pass — `client-ip=23.83.213.23` (validates main-hosting.eu, **not** the From domain) |
| Subject | Update Regarding Your Transfer Request |
| Date | Mon, 27 Jul 2026 18:57:35 +0000 |
| X-Mailer | PHPMailer 7.0.2 |
| Content-Type | text/html; charset=UTF-8 |

The From address displayed to the recipient does not match the Return-Path or the domain that actually authenticated the message (`main-hosting.eu`). This mismatch, combined with a generic `wordpress@` local-part, indicates the message was generated by a mail-sending script or plugin on shared hosting rather than dedicated business mail infrastructure.

## 4. Email Authentication Results (SPF / DKIM / DMARC)

| Test | Result | Status |
|---|---|---|
| SPF | Pass (for `main-hosting.eu` — not the displayed From domain) | ⚠️ Caution |
| DKIM | No DKIM-Signature header present | ❌ Fail |
| DMARC | Fail (alignment failure; policy = `p=NONE, sp=NONE` — not enforced) | ❌ Fail |
| From / Return-Path alignment | Mismatched | ❌ Fail |

SPF passed, but only for `main-hosting.eu`, the infrastructure that actually sent the mail — it provides no authentication for the `imperialtrustgroup.com` identity shown to the recipient. No DKIM signature was present. DMARC alignment therefore failed — but since `imperialtrustgroup.com` publishes `p=NONE, sp=NONE`, the domain owner isn't asking receivers to quarantine or reject failures, which is exactly what let the spoofed message land in the inbox instead of being blocked.

## 5. Infrastructure & WHOIS Findings

### 5.1 Relay IP — `23.83.213.23`
- **Organization:** MailChannels Corporation (MC-733), Vancouver, BC, Canada
- **Resolve Host:** `brown.larch.relay.mailchannels.net`
- **Assessment:** MailChannels is a legitimate outbound spam-filtering relay bundled by default with many cPanel/WHM and shared-hosting platforms, including Hostinger. This IP is shared relay infrastructure, not infrastructure owned by the attacker — it's the last hop before Gmail, not the origin.

### 5.2 Sending domain — `main-hosting.eu`
- **Registrar:** Hostinger operations, UAB
- **Name servers:** any1.hostinger.com / any2.hostinger.com
- **Assessment:** A generic Hostinger shared-hosting mail domain used to route outbound mail for customer accounts on that server — not infrastructure unique to this attacker.

### 5.3 Impersonated domain — `imperialtrustgroup.com`
- **Registrar:** Hostinger operations, UAB
- **Created:** 2026-06-14 — 44 days old at time of the email
- **Name servers:** AURORA.DNS-PARKING.COM / NEBULA.DNS-PARKING.COM
- **Domain status:** Registered And No Website
- **Registrant:** Redacted (WHOIS privacy via Hostinger)

A domain claiming to represent a financial "trust group" that is six weeks old, privacy-shielded, DNS-parked, and has no live website is inconsistent with a genuine, operating financial services business. This pattern — cheap registrar, WHOIS privacy, parked nameservers, no website — is characteristic of infrastructure stood up specifically to lend legitimacy to a phishing or transfer-fraud campaign.

## 7. Investigation Timeline

1. Received email in Gmail; used "Show original" to extract raw headers
2. Identified From/Return-Path mismatch and reviewed SPF / DKIM / DMARC authentication results
3. Confirmed DMARC record exists for `imperialtrustgroup.com` but policy is not enforced (`p=NONE, sp=NONE`), and no aligned DKIM signature is present
4. Extracted source IP (`23.83.213.23`) from the SPF/Authentication-Results headers
5. Performed IP WHOIS / RDAP lookup — resolved to MailChannels Corporation (Vancouver, CA), a legitimate outbound mail-filtering relay used by shared hosting providers
6. Performed reverse DNS (PTR) lookup guidance for `23.83.213.23`, expecting resolution to `*.relay.mailchannels.net`, confirming this is shared relay infrastructure rather than an attacker-owned host
7. Performed domain WHOIS on `main-hosting.eu` and `imperialtrustgroup.com` — both registered via Hostinger operations, UAB
8. Found `imperialtrustgroup.com` was registered 44 days prior to the email, WHOIS-privacy protected, using DNS-parking nameservers, with no live website ("Registered And No Website")
9. Concluded the message is a spoofed / impersonation phishing email using a freshly registered, unused domain as a business lure

## 9. Conclusion

This email is assessed with high confidence to be a phishing message impersonating `imperialtrustgroup.com` in a transfer-fraud / business email compromise (BEC) pretext. The sender does not control the domain shown in the From header, the impersonated domain is newly registered and unused, and the message only reached the inbox because the impersonated domain's DMARC policy was not enforced. No links were clicked and no attachments were opened during this investigation; all analysis was performed passively against headers, DNS, and WHOIS data.

## 10. Recommendations

- Do not click any links or reply to the message; delete or mark as phishing in Gmail to feed Google's abuse detection.
- Report abuse to Hostinger via `abuse-tracker@hostinger.com`, citing both domains and the full header trace.
- If received on an organization-monitored mailbox, escalate to the security/IT team as a targeted BEC attempt and flag the sender/domain for blocklisting at the mail gateway.
- Treat any unsolicited "transfer request" or "update regarding your transfer" email as high-risk regardless of apparent sender authenticity; verify through an independently known contact channel, never via the email itself.
- Broader control recommendation: organizations should publish DMARC with an enforced policy (`p=quarantine` or `p=reject`) rather than `p=none`, to prevent spoofed mail using their domain from reaching recipients.
